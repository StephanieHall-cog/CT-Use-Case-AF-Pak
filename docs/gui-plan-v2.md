# Target-tracking GUI — map layers, link chart and baseball cards (plan v2)

Supersedes the screen list in `docs/gui-plan.md` §3 for the analyst-facing product; the data-model and provenance rules
there still apply. Two of Stephanie's existing apps are the visual and behavioural templates:

| Template | What we copy |
|---|---|
| **UKR Watch** (`StephanieHall-cog/StephanieHall-cog-ukr-watch`, Node/Express + better-sqlite3, MapLibre GL + vis-network, single `public/index.html`) | Shell: dark theme tokens, header tab bar (Map · Entities · Link chart · Review · Admin), login + roles (viewer/analyst/instructor/admin) + audit log, **map with a Layers panel (checkbox per layer), legend, top time-slider, right-hand event feed and a slide-in drawer**, synthetic-mode orange banner and dashed-border cards, event dots sized by corroboration with a translucent **plot-resolution ring**, saved investigations and PNG export on the chart. |
| **netdash** research dashboard (`StephanieHall-cog/research-network-dashboard`) | **Baseball cards**: card front (photo, name + native script, badges, 4 stat tiles, checkbox "select for link chart", ★ POI toggle); card back (header with photo upload / replace / remove, "Make primary subject", "Set as main for link chart", tabbed sections, POI block with priority + reason saved server-side, user-entered contacts table with source column, mini-map of appearances, associates list with "Build link chart from selected"). Link chart: vis-network forceAtlas2 → physics off after stabilisation, 1st/2nd-hop expansion, node rings for strength tiers, click → "Open baseball card". |

Target stack therefore: **Node (Express) + better-sqlite3 over `db/afpak.sqlite`, one static `public/index.html` using MapLibre GL
(OpenFreeMap dark style) and vis-network**, deployable to Fly like the two templates. No React build step — the templates
prove the single-file approach is enough for this scale and it keeps the app auditable.

## 1. Data the GUI reads (all produced by `python3 scripts/build_db.py [--synthetic synthetic/*.json]`)

| Layer / panel | Table(s) | Export |
|---|---|---|
| Attacks and other events by group, by date | `events` + `event_actors` (+ `event_geo` for scenario geometry, `map_plots` for ISW points, `place_coords` for podcast/document places) | `event_points.geojson` (events with explicit geometry), `isw_plots.geojson`, `place_coords.json` |
| USG locations / other-government locations / international orgs / host-nation military / border crossings / soft targets | `sites` (38 public-reference sites, approximate coordinates, `verified=0`, `precision_km`) | `sites.geojson` |
| Target baseball cards | `target_cards` + `entities` + `aliases` + `relationships` + `profiles` (UN/FBI biodata when the card is a real person) | `target_cards.json` (one fully-joined record per card) |
| Selectors and correlations | `selectors` (phone, imsi, imei, email, social, cma_account, vehicle), `selector_links` (same_subscriber, used_with, registered_with, recovery_contact, co_located, frequent_contact, transfers_to) | `selectors.csv`, `selector_links.csv` |
| Last known location and location history | `location_hits` (kind = travel · ss7 · gsm_cdr · isr · humint · open_source; ts, lat/lon, `precision_km`, `selector_id`, detail, confidence); `target_cards.last_hit_id` | `location_hits.geojson` |
| Link chart | `relationships` (podcast / document / UN-stated / synthetic), `memberships`, selector-level edges derived from `selector_links` | `graph.json` |

Dataset boundary (unchanged): every row has `dataset` real|synthetic; synthetic persons have `SP-` ids and can never
resolve to a real person; synthetic edges to real organizations/places are allowed and flagged. **All selector, correlation
and location-hit data in the repo is synthetic** (`synthetic/targets_demo.json`, regenerated by `scripts/synthetic_targets.py`);
real people have *no* selector rows until an analyst enters sourced ones (UKR Watch rule: contact-type fields on real people
are synthetic placeholders marked ⚠︎ until an official/public source is supplied).

## 2. Map tab (UKR Watch layout)

Left: Layers panel. Top-centre: time slider with play button (window = day/week/month; everything on the map and in the
feed filters to the window). Bottom-left: legend for whichever layers are on. Right: event feed (newest first, chips for
group / source / confidence). Click dot → drawer.

Layers (checkbox, colour, source):

1. **Attacks by group** — `event_points` + `isw_plots` + podcast/document events located via `place_coords`; one colour per
   group (Haqqani Network, Taliban, TTP, ISKP, al-Qaeda/AQIS, other, unknown) with a *group multiselect*; marker shape by
   source (circle = scenario/synthetic, square = ISW map plot, diamond = podcast/document claim); translucent ring =
   `precision_km`. Sub-filters: event type (attack, security_operation, control, presence…), confidence, min corroboration.
2. **USG locations** — `sites.kind in (usg_diplomatic, usg_military)`; closed/historical sites hollow.
3. **Other-government locations** — `other_gov_diplomatic`, `other_gov_military`, `host_gov`, `host_gov_military`
   (British Embassy Kabul, Pakistani/Chinese/Russian/Iranian embassies, Indian consulates, Pakistan Army 11 Corps, Bannu
   cantonment…), with an *operator* multiselect.
4. **International orgs / soft targets / infrastructure / border crossings** — remaining `sites.kind` values.
5. **Target last-known locations** — one marker per `target_cards` row at `last_hit_id`, labelled with the objective name,
   coloured by hit kind (ISR red, GSM/CDR orange, SS7 yellow, travel blue, HUMINT grey, open-source green), ring =
   `precision_km`; toggle *trail* to draw the ordered `location_hits` track for the selected target.
6. **ISW map overlay** — select a map from `isw_maps.json`, overlay the image via `image_corners` (already in the data).
7. **Place pins** — podcast/document places (`place_coords`) sized by `n_episodes + n_documents`.

Drawer content for an attack: date (precision), description, groups and named actors (links to cards), source chip
(podcast quote + timestamp / document page / ISW map + legend class / SYNTHETIC scenario), nearby sites within 5 km
("150 m from Embassy of Russia"), "add to investigation". Drawer for a site: name, operator, status, note, `verified` flag with
an "edit coordinates (analyst)" action that writes an override row, and the list of events within N km in the time window.

Queries the map must answer in one click: *attacks claimed by TTP in Bannu district, Jan–Mar 2026*; *all events within 2 km
of a USG or other-government site*; *where was OBJECTIVE GRANITE in the 72 h before the 2026-06-19 Khost attack*.

## 3. Baseball cards (netdash layout)

Entities tab = card grid (filters: dataset, network, priority, tribe, has-selectors, last-hit-within, POI only; sort by
last hit / priority / name). Card **front**: photo (or initials), name, objective name as the badge row headline, chips for
network · tribe · priority · status · dataset, 4 tiles (selectors, location hits, associates, days since last hit).

Card **back** (tabs):

1. **Identity** — name; **variations & kunyas** (from `aliases` for real people incl. UN/FBI spellings and original script;
   `target_cards.kunyas` / `name_variants` for scenario targets); objective name; tribe / sub-tribe; DOB/POB; nationality;
   photo with source line; official profile cards (UN 1988 listing, FBI poster) when present.
2. **Role** — `role_current` ("Khost attack planner", "Head of the Finance Shura revenue committee", "Chief of Security …")
   and `role_history` as a timeline; organization memberships with per-source evidence; for real people the podcast /
   document statements with quote + timestamp/page.
3. **Family & associates** — family edges (`*_of` types) and operational edges (deputy_of, courier_for, supplies, funds,
   protects…) each with source chip; "Build link chart from selected".
4. **Selectors** — grouped table: phones (number, provider, country, first/last seen), IMSI, IMEI (make), e-mail, social
   handles (platform), CMA / mobile-money accounts (name, platform, linked number/e-mail), vehicles (make/model/colour/year,
   plate). Every row shows confidence and source; synthetic rows carry the ⚠︎ synthetic marker; analysts can add sourced
   rows (`entity_fields`-style table with `source_url`, `edited_by`).
5. **Correlations** — a small vis-network drawn from `selector_links`: *phone A ─same_subscriber─ IMSI ─used_with─ IMEI
   ─co_located─ vehicle; phone ─registered_with─ WhatsApp; e-mail ─recovery_contact─ Facebook; CMA account ─transfers_to─
   another target's phone*. Edge label = relation, tooltip = evidence text; cross-target links are highlighted (e.g. the
   courier's IMEI carrying the planner's IMSI for two days) and a button jumps to the other card.
6. **Location** — "Most recent known location" header card: kind, timestamp, place, lat/lon, precision, detail (tower LAC/CID,
   border-crossing record, ISR dwell, SS7 answer), selector that produced it; below it the full hit history table and a
   mini-map (MapLibre) with the trail and nearby sites; a "show on main map" button.
7. **Sources** — every statement on the card with its provenance (episode + timestamp, document + page, UN reference,
   FBI poster, scenario file), plus the analyst edits audit.

POI block, photo upload and "Make primary subject / Set as main for link chart" are copied verbatim from netdash.

## 4. Link chart tab

vis-network as in both templates: pick a main entity (from a card or search), choose hop depth (1/2), edge-type checkboxes
grouped as *podcast · document · UN-stated · synthetic* and *family · command · finance · logistics · membership · selector*;
toggle "collapse selectors" (people-only graph) vs "expand selectors" (phones/IMEIs/accounts become nodes, so a shared IMEI or
CMA transfer visibly bridges two people). Node glyphs: person / organization / place / selector-kind icons; synthetic nodes
dashed; POIs red ring; node size = degree in current view. Right panel: evidence for the selected edge; "Open baseball card";
saved investigations (JSON in `investigations`, as UKR Watch), PNG export, physics off after stabilisation with a "Resume
motion" button.

## 5. API (Express, mirrors UKR Watch routes)

`GET /api/events?from&to&groups&types&sources&bbox` → GeoJSON · `GET /api/sites?kinds&operators` · `GET /api/targets?filters`
(card fronts) · `GET /api/targets/:id` (= one `target_cards.json` record) · `GET /api/targets/:id/hits` · `GET /api/selectors/:id/links`
· `GET /api/graph?root&depth&types&expandSelectors` · `GET /api/maps`, `/api/maps/:id` (ISW overlays) · `POST /api/targets/:id/fields`,
`/api/targets/:id/poi`, `/api/sites/:id/override`, `/api/investigations` (analyst writes, audited) · `GET /api/stream` (SSE for
new events) · `POST /api/login`, `/api/logout`, `/api/users` (admin). Real-data tables stay read-only; analyst writes go to
`entity_fields` / `overrides` / `investigations` / `audit` exactly as in UKR Watch.

## 7. Guardrails

- Banner on every screen: real rows = *as stated by the source shown*; synthetic rows = *fictional, for demonstration*.
- A real person's card never shows a selector, correlation or location hit unless an analyst entered it with a source; the
  demo cards are all `SP-` entities.
- Site coordinates and ISW plot positions show their precision; nothing is drawn as a precise point without a ring.
- Analyst edits never mutate real rows; they are overrides with user + timestamp (audit table), reversible.
